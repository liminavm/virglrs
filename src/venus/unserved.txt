# The venus commands this build does not serve, and why each one is here.
#
# This file also decides what a guest is offered. Our `vkEnumerateDeviceExtensionProperties` answer
# is every extension the host driver has and the pinned vk.xml can serialize, minus each one a
# guest could only use by sending a line below -- and minus what depends on one of those. Every
# status but `not-in-reference` withholds (`ledger::Status::withholds` says why); serving an
# extension's last line is what puts it back. The capset's mask is not this list: it only says
# which structs the guest's encoder may use.
#
# Withholding cannot close the ledger. Core commands of the version the guest is told are its to
# send whatever the extension list says, and some lines below are core, down to 1.0. So the ledger
# is closed by serving. A guest that sends a line anyway poisons its context. That is the right
# answer -- a zeroed reply is shaped exactly like a successful one, so there is no safe way to
# continue -- but it is only the right answer while the set is a decision rather than an accident.
#
# This file is that decision, and a bare list of names could not be: it says nothing about whether
# a line is work we owe or a command nothing here can reach. So each line carries a
# `status:group`, and `every_command_the_protocol_defines_is_served_or_on_the_ledger` holds the
# whole file to it -- serving a command means deleting its line, and a protocol bump that adds one
# means adding a line with a status.
#
#   wanted            The reference serves it, this host can run it, and a guest here can emit it.
#                     This is the work, and `group` is the unit to do it in: one probe program per
#                     group, RED against this build and GREEN against the C, then the handlers.
#   out-of-reach      No supported host's guest venus device advertises the extension, so nothing
#                     that runs here can send it. Serving it would mean a `try_` accessor that
#                     refuses by name -- there is no test that could go green. The bar is every
#                     host, not the one at hand: a command out of reach on KosmicKrisp and
#                     reachable on anv is `wanted`, and four groups below moved that way once the
#                     Linux guest was asked.
#   no-host-feature   The extension or core version is there, but the command needs a device
#                     feature no supported host driver reports, so no host here can run it and no
#                     probe could pass its positive control. `vkQueueBindSparse` needs
#                     `sparseBinding`, false on KosmicKrisp and on anv. Wanted again when a host
#                     reports the feature.
#   not-in-reference  The C refuses it too. Mostly commands the venus driver answers guest-side
#                     and never puts on the wire. Not a gap against the reference; a decision.
#
# The counts are measured, not estimated: every status was cut against the extension lists of real
# guest venus devices -- one per supported host -- and not against vk.xml or the host driver. The
# Linux guest advertises 169 device extensions on anv, and every `wanted` group's extension is
# among them, so nothing here is wanted on one host and out of reach on the other.
#
# What a line here costs, when a guest reaches it: nothing guest-side names the command. Poisoning
# is the right answer and it is still not a diagnosable one -- the guest's next call fails, its
# driver reports that failure in its own vocabulary, and the shape of that is a resource error.
# `vkQueueSubmit2` was measured: zink reported VK_ERROR_OUT_OF_HOST_MEMORY from
# vkEndCommandBuffer, then "couldn't allocate memory", then GL_OUT_OF_MEMORY in glReadPixels, and
# then deadlocked with every thread in futex_wait on a fence the dead context would never signal.
# The test above it saw only its own timeout. The `[virglrs] refused:` line in the worker log is
# the ONLY place the command is named -- so read that log first, and never diagnose a guest-side
# OOM or hang without it.
#
# A `wanted` line is not a promise that anything reaches it today, and not a promise that nothing
# does. A seated synoik session plus all 33 glmark2 scenes plus two indexed-draw probes refused
# nothing, because zink emits `vkCmdDrawMultiIndexedEXT` -- which this build serves -- wherever
# a plain `vkCmdDrawIndexed` would appear. A stock Fedora 44 desktop, measured
# 2026-09-08, refuses `vkCreateBufferView` repeatedly while it is merely running.
#
# What a Linux guest reaches, measured on anv with the poisoning taken out so a boot could count
# more than one: vkmark's whole scene set, twice over with its non-default options, reaches
# nothing on this list at all. Nor does zink: the one command it sent, from glmark2 on wayland
# and from kmscube on KMS, was `vkCmdSetColorWriteEnableEXT`, which is served. A GNOME desktop
# with a venus client on it -- vkcube composited by gnome-shell -- reaches nothing on this list
# either.
#
# So a workload census cannot enumerate this file: the first unserved command kills the context,
# so a boot discovers exactly one and says nothing about the rest. Reach these deliberately, with
# a program that names the command -- `harness/probes/` is one per group.
#
# And read the worker log, not the program. A guest reads a zeroed reply as success, and venus
# answers some commands guest-side without asking the host at all, so a probe can report `ok` for
# a command that was refused: measured on the events group, where vkCreateEvent was refused and
# the next four checks still passed. `[virglrs] refused:` is the oracle. The program is not.
